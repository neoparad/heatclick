作成: 2026-11-20。設計の正本は [2026-11-19-ugokilink-master-architecture-v2.md](2026-11-19-ugokilink-master-architecture-v2.md)（以下「設計書」）。この計画は、設計書の §13（31 の手順）を「エージェントが止まらずに最後まで作れる形」に並べ直したものである。

## 0. 3 行要約

- 設計書の手順 0〜30 を、8 つの波に分けて最後まで作る。途中で承認を待たない。レビューは全部終わった後にまとめて行う。

## 1. 進め方の原則

**速さを優先する。** 次の 5 つを守る。

1. **止まらない。** 承認・確認・レビューのために作業を止めない。迷ったら設計書の「推奨」を採り、理由を 1 行 `docs/ugokilink/BUILD_LOG.md` に書いて進む。
2. **設計書と食い違ったら、動く方を選んで記録する。** 設計書の記述が実コードや外部の仕様と合わない時は、設計書の意図に最も近い実装を選び、`BUILD_LOG.md` に「設計書の §、実際にしたこと、理由」を残す。設計書そのものは書き換えない。
3. **並行できるものは並行する。** 各波の中の作業の束（以下「束」）は、触るディレクトリを分けてある。束どうしで同じファイルを触らない。
4. **試験は書くが、通すために止まらない。** 各束は自分の試験を付ける。ほかの束の未完成で通らない試験は、理由を付けて保留の印を付け、進む。最後の波で保留を 0 にする。
5. **1 つの束 = 1 つ以上のコミット。** コミットの形式は `<type>(scope): <英語の説明>`。作業ブランチは 1 本（`feat/ugokilink-v2`）。PR を束ごとに分けてレビューを待つことはしない。

**「できた」の定義（束ごと）**: コードがある。試験がある。手元で `npm run type-check` と、その束の試験が通る。本番に要る作業が §7 に書いてある。ゲートの状態（開／閉と、開く条件）がゲート台帳に載っている。

## 2. 触らないもの（これだけは例外なし）

承認の手続きではなく、エージェントが実行しない操作の一覧である。該当したら、ファイルと手順書を作って次へ進む。

- **本番への適用をしない。** 本番の DDL、本番データの削除・書き換え、デプロイ（Vercel・Cloudflare とも）、worktree からのデプロイ。移行は `migrations/` にファイルで置き、適用の手順を §7 に積む。
- **秘密の値に触らない。** `.env*` を開かない・コミットしない。新しく要る鍵は、名前と用途だけを `env.example` に足す。
- **触らない場所**: 旧 ugokimap（別リポジトリ）の `app/*`、`reference/components/` 系の見本。
- **今動いているものを壊さない。** 既存の画面・API・Worker・定期実行は、置き換えが動くまで残す。新しいものは別の場所に足す（§3）。`npm run build` を、始めた時点より悪くしない。
- **テナントの指定を落とさない。** すべての DB 操作と API 呼び出しで `tenant_id` を持ち、検証する。
- **見本データを返さない。** データが無い時は、作り物ではなく `not_collected` などの状態を返す。
- **push しない。** リポジトリは公開で、作業資料には未修正の弱点が行番号つきで載っている。コミットは手元で自由に行い、push はオーナーが決める。

## 4. 「作り終える」と「ゲートを開ける」を分ける

設計書のゲートには、エージェントが今日は通せないものが 4 種類ある。どれも止まる理由にしない。

- **オーナーの判断が要るもの（判断 1〜31）**: 設計書の「推奨」の側で作る。機能は判断ごとの許可の印で包み、既定は `not_entitled`。判断が記録されたら印を替えるだけで開く形にする。
- **法務の確認が要るもの**: 同じ扱い。確認に要る材料（開示の文面、項目の一覧）は自動で出せるようにしておく。
- **実データの蓄積が要るもの**（例: 旧新の換算比 ±5%、SDK の重さの検定で各群 3 万件）: 判定するプログラムと、作り物のデータでの試験までを作る。本物のデータでの判定は、ゲート台帳が「今いくつ・あといくつ」で示す。
- **本番への適用が要るもの**: ファイルと手順書を作り、§7 に積む。

判断の中で、作りの形を変えるものが 4 つある。どれも設定で切り替えられるように作る。

- **判断 1（同意のモード）**: 5 つのモードすべてを実装する。サイトの既定は設定束で配る。
- **判断 29（保存の地域）**: 保存先を地域つきの設定にし、所在を照らす検査（§11.11 の 13）を付ける。保存先の種類を替えられるよう、保存の層を 1 枚かませる。
- **判断 31（基盤モデルと Jev の出力）**: 生成モデルは 2 つの候補のどちらでも動くように作る。Jev の出力を学習に使う経路は作らない（許可が記録された時に足す）。
- **判断 28（ソースの公開）**: 公開する部分（`packages/`、受付）と公開しない部分（ボット判別の規則、モデル、鍵）を、最初からディレクトリで分ける。

## 5. 作業の波

### 波 0: 足元の後始末（手順 0）

今動いているコードの穴を先にふさぐ。契約の定義を待たない。

- **0-A 止血**: 本番経路の見本データ（約 45 か所）と AI 流入の合成行を消し、`not_collected` を返す。SQL に値を直接埋めている 4 か所と、テナント指定の無い問い 4 つを直す。場所は `facts/repo-saas-collection.md`・`repo-saas-delivery.md`・`repo-saas-fusion.md` にある。
- **0-B 定期実行と旧ジョブ**: 定期実行の一覧（持ち主と止め方）を作る。登録だけ残った Inngest ジョブを 0 にする。今ある定期実行は、置き換えが動くまで止めない。
- **0-C 現状の記録の道具**: 本番のテーブル定義・版・利用者の一覧、旧データの全数調査を取る読み取り専用のスクリプトを作る（実行はオーナー）。決定の台帳の入れ物を作る。
- **0-D 取り戻せない時計**: アドレス一覧と鍵の一覧を毎晩保存する仕組みを作る。Search Console の一括書き出しの設定手順を §7 に積む。

  - データの組: 学習用・選定用・最終の評価用の 3 つに、ページの系譜とほぼ同じ文を境界にして分ける。出どころの検査（訪問者の行・許可の無いテナントの文・Jev の出力が 0 件）。ほぼ同じ文の除去、疑わしい例の隔離。管理主体ごとの重みの上限（3 分の 1）は、複数の管理主体が参加する共同の学習に掛ける（自社の文だけの最初の部品には掛からない）。
  - 学習: 仕事ごとの追加部品のジョブ（基盤モデルと追加部品はサーバーでだけ動かす）。テナント専用の学習と共通の学習を分ける。共通の学習は、判断 31 の (c) まで自社サイトの文だけ。
  - 評価と昇格: 事前登録した指標と件数、差の信頼区間の下限、守りの試験と仕込みの試験、§8.8 の全手順、見張り、別名での巻き戻し。仮説用の部品も、学習・評価・昇格の判定まで実装する。有効な実験の結果が届くたびに挑戦者を更新し、必要な独立した実験の数と評価の条件がそろうまで昇格を閉じる。
  - 削除: 24 時間以内に部品と派生物を利用から外す仕組み、14 日以内の削除の証明、含まない状態からの学習し直し。
  - 軽い分類器への写し（先生は自前のモデル。50 KB・整数演算・署名のゲート）。配布物へのライセンスの文の同梱。
  - **Jev の出力は学習の正解に使わない**（Jev の利用規約）。GPU の計算基盤の契約（学習用と本番の推論用）は §7。

### 波 6: 広げる（手順 21〜28）

前提: 波 4 と波 5。番号順ではなく、前提がそろった束から始める。

機械学習の各機能は、最下段（ルールや無作為）から上の段までを全部作る。上の段は挑戦者として登録し、昇格の判定（§8.8）は実データがたまるまで閉じたままにする。生成モデルによる強化（§8.12 の「ML の各機能の強化」）も、それぞれの束で挑戦者として入れる。

## 6. LINKTH CRAWL 側の作業

設計書の §15 にある 15 群は、別のリポジトリの作業である。このリポジトリの作業はそれを待たない。

- LINK 側は、CRAWL の口を「契約どおりに答える代役」で埋めて作り、試験する。2-C の 2 つ目の描画環境があるので、最初の無作為試験までは CRAWL の変更が無くても進められる（§13.8）。
- CRAWL 側を作る時は、本線の作業ツリーで行う（手元の古いチェックアウトは本線より約 1,200 コミット古い）。オーナーが Antigravity に本線を開かせた時に、§15 の 1〜15 を、資料 `facts/repo-crawl-*.md` と `consistency-sequence.md` の CRAWL の順序に沿って作る。原則は §1・§2 と同じ。

## 7. オーナーの作業（止まる理由にしない。`docs/ugokilink/OWNER_TODO.md` に積む）

エージェントは、下の種類の作業が出るたびに、手順・前提・確かめ方を 1 件ずつ書き足す。

- **本番への適用**: 移行の適用、Worker と Vercel のデプロイ、旧データの全数調査の実行、旧システムの停止。
- **鍵と設定**: 新しい環境変数の値、オフラインで保管する署名の鍵、2 人目の鍵の担当者。
- **外部の手続き**: Search Console の一括書き出しの有効化、別オリジン枠のドメイン登録、法務への確認依頼、有償の人間パネル、外部の計算基盤の契約。
- **自社 5 サイトでの作業**: スニペットの貼り付け、開示の文面の掲載、サーバーと CDN のログを消さずに残す設定。
- **判断**: 設計書 §14 の判断 1〜31。期限つきのもの（判断 1、8 の (b)、12、14、29 など）は、台帳の先頭に置く。

## 8. 完了報告（最後に 1 回）

全部の波が終わったら、`docs/ugokilink/COMPLETION_REPORT.md` に次を書く。レビューと修正は、この報告をもとに後から行う。

- 束ごとの状態: 作り終えた／一部／作っていない（理由つき）。
- ゲートごとの状態: 開いている／閉じている（何で開くか）。
- 設計書と変えたところ（`BUILD_LOG.md` の要約）。
- 試験の結果: 通った数、保留の数（0 が目標）、手元で確かめられなかったもの。
- 既知の弱点と、次に直すべき順。
