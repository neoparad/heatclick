## 0. 要約（3行）

1. **3案の方向は正しいが、根本原因の見立てがずれている。** 遅さ・メモリ超過の主因は scroll の行数より、`events` テーブルの並び順が「サイト→時刻」だけで、URL や種別で絞れないこと。
2. **柱②が守ろうとしている「迷い率・速度ペルソナ」は、どこからも呼ばれていない死にコード。** 途中の scroll 行は不要なので、85%ではなく95%超を削れる。加えて全体の約1割（anchor / alt）は中身が保存時に捨てられた行。
3. **3案の外に、もっと急ぐ問題がある。** 定期ジョブ3本が動いていない疑い、AIチャットのSQL組み立ての穴、バックアップと削除APIがリポジトリ上に存在しないこと。

## 前提と限界

- 本番 ClickHouse には接続できない（接続元IP制限）。テーブル構造は `scripts/setup-server.sh:79-103`、`docs/SPECIFICATIONS.md`、`migrations/2026-05-17-sprint0-tenant-isolation.sql` からの**推定**。本番の実物は末尾の確認リストで要確認。
- 裏取りの度合いを各項目に付けた。**［確認済］** は自分でコードを読んだもの、**［未検証］** は補助エージェントの報告のみのもの。

## 1. 3案への批判的レビュー

### 1.1 柱③ ClickHouse（最重要）

**結論：TTL と集計ビューを既存テーブルに継ぎ足すより、scroll 生データを別テーブルに分け、`events` は正しい並び順で作り直すべき。**

#### 原因の見立て

- **並び順が原因。** ［確認済・リポジトリ定義］ `ORDER BY (site_id, timestamp)`、月別区切り。ヒートマップは1ページ分を見るだけでも、そのサイトの期間内の全行を読む。`url` も `event_type` も `tenant_id` も並び順に入っていない。
- **URL を毎行、正規表現で加工して比較している。** ［確認済］ `lib/heatmap/canonical-url.ts:38`。書き込み時に正規化済みURLを列として持つべき。
- **scroll 層と exit 層が一字一句同じクエリ。** ［確認済］ `app/api/heatmap/route.ts:581` と `:611`。同じ全走査を2回している。しかも `event_type='scroll'` の絞り込みが無く、全種別の行を読む。
- **セグメント絞り込みでさらにもう1回走る。** ［確認済］ `lib/heatmap/segment-filter.ts`。
- **期間の既定値が無制限。** ［確認済］ 1970年〜2099年。期間指定なしの呼び出しは全履歴を読む。
- **4.54GiB はサーバー全体の上限の可能性がある。** その場合、重い読み取り中は書き込みも失敗する。Worker は失敗分をログに出すだけで再送しない（`workers/event-ingest/src/worker.ts:989`）。つまり「遅い」だけでなく「計測が欠ける」問題になる。

#### MergeTree 特有の注意点

| 提案メモの案 | 落とし穴 |
|---|---|
| 条件付きTTLで scroll だけ消す | 行単位の削除になり、月ごとのデータの塊を全列まるごと書き直す。削除のたびにディスクとメモリを食う |
| 既存テーブルに TTL を設定 | 既定では設定した瞬間に既存7,450万行すべての書き直しが始まる。4.5GiBの箱では障害の引き金になり得る |
| 集計ビューで最大値を事前集計 | 挿入された塊（現状10行）しか見ない。「最大値の途中状態」を持つ型が必須で、読む側も再集計が要る |
| 集計ビューで往復回数・速度 | 行をまたぐ計算はビューでは作れない。ブラウザ側で計算して送るしかない |
| 集計ビューを追加 | 既存データには遡らない。1回の挿入で作られる断片も増える |

補足：

- **サーバー側まとめ書き（async_insert）が未使用。** ［確認済］ Worker は1リクエストごと・テーブルごとに10行以下の小さな挿入を出している。集計ビューを足す前にこれを有効にしないと、断片が多すぎて書き込みが止まる障害（too many parts）に近づく。
- **テナント列を並び順の先頭に入れられない。** 後から追加した列は先頭にできない。作り直しが唯一の方法。
- **座標の型が小さい。** ［確認済・リポジトリ定義］ `scroll_y` / `click_y` が65,535pxまでの型。長いページで値が壊れる。作り直しの際に一緒に直す。
- **端末の時計をそのまま区切りに使っている。** ［確認済］ Worker は端末が送った時刻を秒単位に丸めて保存する。狂った時計の端末が過去・未来の月の断片を作る。区切りはサーバー受信時刻で切るべき。

#### 代替案

1. **scroll（またはその後継）を専用テーブルへ。** Worker はすでに種別ごとにテーブルを振り分けている（`worker.ts:337`）。日単位で区切り、サーバー受信時刻で古い日を塊ごと捨てる。削除コストはほぼゼロ。
2. **セッション×URL の要約テーブルを新設。** 並び順は「テナント→サイト→正規化URL→日付」。ヒートマップの scroll / exit / セグメントはここだけを読む。
3. **`events_v2` へ作り直し移行。** 正しい並び順、大きい座標型、正規化URL列、受信時刻列、計測スクリプトの版列を持たせ、月単位でコピーして切り替える。並び順の候補は実際の重いクエリ（`system.query_log`）を見て決める。
4. **読み取りユーザーの設定で止血。** 1クエリのメモリ上限と、メモリが足りないときディスクに逃がす設定を、ユーザー側の既定として入れる（読み取り専用ユーザーはクエリ単位で変えられないため）。
5. **メモリ増設も選択肢。** 上の対策と排他ではない。数千万行規模で5GB弱は余裕が無い。

### 1.2 柱② スマート計測

**結論：4ルールのうち「折り返し頂点」と「1秒ごとの移動サンプル」は不要。代わりに「ページ単位の累積スナップショット」を送る方式を勧める。**

#### 根拠の崩れ

- **`lib/analysis-axes.ts` を読み込んでいるファイルはゼロ。** ［確認済］ 迷い率・速度ペルソナは実行されていない。しかもこの2つのクエリはテナント条件も期間条件も無く、もし動かせば全 scroll 行を走査する。
- **実際に scroll を使っている箇所は2種類だけ。** ［確認済］ 「セッションごとの最大値」（ヒートマップ、ページ統計、セグメント）と「行の単純平均」（下記4箇所）。
- **「1秒ごとのサンプル」を残すと85%に届かない恐れ。** ゆっくり読む人ほど行が出続ける。

#### 推奨する送り方

- **5%刻みで新しい深さに達した時点で即送る。** ヒートマップが5%刻みで集計しているため、解像度が一致する。10%刻みだと半分に落ちる。
- **累積スナップショットを送る。** 中身は最大到達px、その時点のページ全体の高さ、往復回数、実際に見ていた時間。停止時・画面が隠れた時（`visibilitychange` / `pagehide`）に上書き送信する。
- **往復回数と速度はブラウザで数える。** すでに `tracking-ext-behavior.js` が往復を数えている。

#### 精度が落ちるエッジケース

- **モバイルでは離脱イベントが届かない。** ［確認済］ 最終到達点の送信は `beforeunload` だけ（`public/v2/tracking.js:643`）。画面が隠れた時の処理は `read_area` しか送らない。「離脱時の最終点」に頼る設計はスマホで欠ける。
- **ページの高さが後から伸びる。** 遅延画像や開閉メニューで到達率がずれる。px で持って描画時に割り直すのが正解だが、`document_height` は毎回送られているのに Worker の保存列に無く捨てられている（`worker.ts:238`）。
- **画面より短いページは常に0%。** ［確認済］ `tracking.js:554`。全部見えているのに「離脱0%」扱いになる。
- **SPA（ページ遷移なしで画面が変わるサイト）で最大深度がリセットされない。** ［確認済］ `tracking.js:514`。2ページ目に1ページ目の値が持ち越される。
- **行の単純平均を使う4箇所が、切替日に段差になる。** ［確認済］ `app/api/fusion/url-summary/route.ts:50`、`app/api/site-doc/route.ts:64`、`lib/heatmap/agent-heatmap-client.ts:393`、`lib/llm/hybrid-query.ts:1182` / `:2675`。「セッション最大値の平均」に定義を変え、計測スクリプトの版を保存して前後を区別できるようにする。
- **離脱時の送信には合計約64KBの上限がある。** 拡張の集計をまとめて離脱時に送ると、後ろの分は黙って落ちる。
- **全イベントに同じ情報を毎回付けている。** ［確認済］ ブラウザ名、ボット判定のJSON、流入元など（`tracking.js:401`）。行数を減らしても、1行あたりの無駄は残る。

### 1.3 柱① Inngest

**結論：つなぎ直さないことを勧める。まず旧ジョブを今日止めるのが先。**

- **旧 `warm-heatmap-cache` の向き先を確認する。** 本番 ClickHouse を叩いているなら、6時間ごとに300回の重いクエリを投げており、メモリ超過の直接原因の1つ。停止はコード不要。
- **死活監視は、監視対象の外に置く。** Inngest は Vercel 上の関数を呼ぶだけなので、Vercel のデプロイが壊れると監視も一緒に止まる。書き込み失敗は Worker がその場で分かるので、Worker から通知するのが最短。
- **バックアップは ClickHouse のサーバー上で動かす。** Vercel から SSH させると、SSH鍵を Vercel に置くことになる。
- **削除請求は日次の定期ジョブで足りる。** 請求テーブルを見て14日経過分を消すだけ。
- **Vercel の関数は既定で300秒まで動き、定期実行もすでに4本ある。** 入れるなら、長時間・多段のクロール同期（LINKTH CRAWL × GSC / GA4）だけに絞るのが妥当。
- **既存の定期ジョブ3本が動いていない疑いがある（3.1参照）。** 仕組みを増やす前に、今ある仕組みが動いているかの確認が先。

## 2. scroll 以外の無駄と歪み

### 2.1 使われていないのに負荷を生んでいるイベント

| イベント | 実態 | 推奨 |
|---|---|---|
| `alt_read_signal`（276万行） | 4項目すべて保存列に無く、空の行。「画像にマウスが乗った」だけで1件。顧客サイトの `img.alt` を書き換え不能にする副作用あり（`tracking.js:704`） | 即停止 |
| `scroll_anchor_hit`（480万行） | 見出し文言・位置・滞在時間が捨てられ、残るのはセレクタだけ。画面からの利用なし | 停止、または専用テーブル化 |
| `scroll_timeline` | 200msタイマーが常時動くが、座標配列は Worker で捨てられ、読むコードもゼロ | 即停止 |
| `image_visibility` | `image_y` で送り、保存列は `element_y`。画面（`app/api/heatmap/elements/route.ts:468`）が使う画像の位置が0になっている可能性が高い | 項目名を揃える |
| `active_time` / `text_node_dwell` / `element_visibility_v2` | 項目名の不一致で主要な値が欠落 | 揃えるか停止 |

すべて［確認済］。`alt_read_signal` などがアプリ側で登場するのは、AIチャットの許可リスト（`lib/llm/hybrid-query.ts:2469`）だけ。

### 2.2 設計上の歪み

- **拡張の集計はすべて離脱時送信。** スマホではほぼ届かず、データがPCに偏る。
- **1PVごとに11ファイルを取りに行く。** ［確認済］ 本体＋拡張10本。キャッシュ指定が無く（`next.config.js`）、毎回 Vercel に問い合わせる。1ファイルにまとめ、版番号つきURLで長期キャッシュすべき。
- **DOM の変化のたびに重い要素検索が走る。** ［確認済］ `tracking-ext-element.js` と `tracking-ext-image.js`。間引きが無く、顧客サイトの操作応答を悪化させ得る。
- **監視対象の要素が広すぎる。** ［確認済］ `[class*="btn"]` などで1ページ数百要素を監視する。
- **`public/` 直下と `public/v2/` に同じスクリプト群が二重にある。** ［確認済］ 配布されているのは v2 だけ（`app/api/install/route.ts:41`）。片方だけ直す事故の元。
- **URL が生のまま保存される。** ［確認済］ 計測スクリプトには URL を掃除する関数があるのに、イベントの `url` には通していない。クエリ文字列に個人情報が入るサイトでは、そのまま保存される。
- **保存列の一覧と送信項目が別々に手で管理されている。** 2.1 の欠落はすべてこれが原因。共通の定義から両方を作るか、突合テストを入れる。

## 3. 他に詰めるべき重要課題（急ぐ順）

### 3.1 定期ジョブ3本が動いていない疑い ［確認済・本番ログ未確認］

Vercel の定期実行は GET で呼ぶが、`app/api/cron/daily-site-summary`、`deep-research`、`fusion-ingest` の3本は処理が POST にしか無く、GET には 405（拒否）を返す。失敗は黙って起きる。残る1本（`app/api/experiments/pool/route.ts:56`）は共通の認証関数を使わず、独自の判定をしている。

### 3.2 AIチャットのSQL組み立ての穴 ［確認済］

`lib/llm/hybrid-query.ts:1692`、`:1716`、`:2085`、`:2109` で、ページURLを文字列のままSQLに埋め込んでいる。入力検証（`lib/llm/analytics-tools.ts:255`）は「空でない文字列」だけ。他テナントのデータを読まれる恐れがある。修正はテナント分離にかかわるため、二重レビュー対象。

### 3.3 バックアップと削除APIがリポジトリ上に存在しない ［確認済］

どちらも `inngest.config.ts` のコメントだけ。バックアップがリポジトリ外で取られているかは要確認。

### 3.4 取り込み口の守りが弱い ［確認済］

- Origin ヘッダー無しのリクエストは検証を素通りする（`worker.ts:197`）。サイトIDは公開情報なので、偽データを流し込める。
- 流量制限は Worker の1インスタンス内の記憶だけで、全体では効かない。
- テナント別・プラン別の上限が無い。1顧客の暴走が全体を止める。
- 書き込み失敗時の再送・退避が無い。

### 3.5 監視が「誰かが見に来た時だけ」動く ［確認済］

`lib/monitoring/ingest-freshness.ts` は `/api/health` が呼ばれた時にしか走らず、それを定期的に呼ぶ仕組みがリポジトリに無い。10日間の無音停止の再発防止として作られたが、現状では通知が飛ばない。

### 3.6 外部テナント受け入れ前の穴

- `USER_REGISTRY=db` でないと社内ユーザー固定になる（`lib/auth/user-registry.ts:26`）。［確認済］
- `public/recording.js:77` は外部ライブラリを版固定なし・改ざん検知なしで読み込む。［確認済］
- `tenant_id` 条件の無いクエリが4箇所ある（`app/api/site-doc/route.ts:66`、`app/api/performance/route.ts:61`、`app/api/fusion/url-summary/route.ts:52`、`lib/aiseo/crawler-acquisition.ts:238`）。［未検証］
- `pagespeed`・スクリーンショット・`site-doc` など有料API・重い処理に流量制限が無い。［未検証］
- Redis が無いと流量制限がインスタンス内の記憶に落ちる（`lib/rate-limit.ts:68`）。［未検証］
- スクリーンショットの重複撮影防止が、Redis 障害時に素通しになる（`lib/heatmap/r2-screenshot-cache.ts:626`）。［未検証］
- `admin-user.json`（メールとパスワードのハッシュ）と `init-default-user.sql` がコミット済み。［未検証］

## 4. 判断ポイント

- **scroll の送り方：累積スナップショット方式（推奨）** → 行数95%超減、スマホでも欠けない。ただし平均スクロール率の定義が切り替わる。メモ案の4ルールなら、使われていない分析のために行を残す。
- **ClickHouse：新テーブルへ作り直し（推奨）** → 並び順・型・テナント列を一度に直せる。月単位コピーの移行作業が要る。継ぎ足しなら作業は小さいが、URLで絞れない問題は残る。
- **Inngest：つなぎ直さない（推奨）** → 管理するサービスが1つ減る。つなぎ直すなら多段ジョブは楽になるが、監視は共倒れになる。

## 5. 推奨の進め方

| 段階 | 内容 | コード変更 |
|---|---|---|
| 0. 確認 | 旧 Inngest ジョブ停止、下の確認リスト | なし |
| 1. 止血 | 定期ジョブのGET対応、SQL組み立ての修正、空イベントの送信停止、scroll/exit の重複クエリ統合、まとめ書き有効化、Worker の失敗通知 | 小 |
| 2. 計測と保存の作り替え | スマート計測、scroll 専用テーブル、セッション×URL 要約テーブル、ページ高さと版の保存 | 中 |
| 3. 土台の作り直し | `events_v2` 移行、バックアップ、削除API、テナント別上限 | 大 |

段階1は互いに独立で、1つずつ出せる。段階2は計測スクリプトと Worker と ClickHouse を同時に変えるため、Worker が新旧両方の形式を受けられる状態を先に作る。

## 6. オーナー側で確認が必要な点

1. `SHOW CREATE TABLE clickinsight.events` の実物（並び順、区切り、`scroll_y` の型）。
2. メモリ超過エラーの文言が「total（サーバー全体）」か「for query（1クエリ）」か。サーバーの搭載メモリ。
3. `system.query_log` でメモリ消費の大きいクエリ上位。並び順を決める材料になる。
4. Vercel のログで定期ジョブ3本が 405 になっているか。
5. 旧 Inngest ジョブの向き先（本番 ClickHouse かどうか）。
6. `SELECT max(scroll_y), max(click_y) FROM clickinsight.events` が 65,535 に張り付いていないか。
7. `image_visibility` の `element_y` が実際に0ばかりか。
8. 本番の `USER_REGISTRY` と `REDIS_URL` の設定有無。
9. バックアップが実際に取られているか、復元を試したことがあるか。
