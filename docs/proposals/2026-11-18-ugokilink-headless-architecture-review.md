## 0. 要約（3行）

1. **転換は筋が良い。** 計算の中身（`lib/` 約5.2万行）は画面からほぼ独立しており、型つきの分析ツール約25本がAIチャット専用で眠っている。これがそのまま MCP の土台になる。
2. **最大の落とし穴は「見本データが本物の顔をして返る」こと。** 画面なら人が気づけるが、API / MCP では AI が作り物の数字を根拠に提案する。最初にやるべきは新機能ではなく、これを止めること。
3. **最短で価値が出るのは、既存の7,450万行を「嘘をつかない読み取りAPI」として出すこと。** 計測の変更も機械学習も要らない。Popup とおすすめの配信は最後（顧客サイトに書き込む機能で、リスクが最も大きいため）。

## 前提と限界

- 本番 ClickHouse には接続できない（接続元制限）。表の定義はリポジトリ内の文書とスクリプトからの推定。
- 裏取りの度合いを付けた。**［確認済］** は自分でコードを読んだもの、**［報告］** は補助調査の報告で自分では読んでいないもの。
- 4つの核の現在地：

| 核 | 現在地 |
|---|---|
| 1. JS計測＋ログ取り込み、AIエージェント統合 | JS計測は本番稼働。ログ取り込みは存在しない。AIクローラーの数字は作り物に退避する |
| 2. 自動学習と3つの出力（Popup / LP改善 / おすすめ） | 学習済みモデルはゼロ。Popup は規則で動くが主要条件が無効。LP改善は規則ベースの実物あり。おすすめは無し |
| 3. LINKTH CRAWL との突合 | URL 正規化の関数はあるが、保存にも照合にも使われていない。構造データの入口はクロール側で閉じている |
| 4. 負債の解消 | 所在は特定済み（基盤レビュー参照）。定期ジョブ3本の修正のみ着手済み |

## 2. 落とし穴と設計案

### 2.1 落とし穴（重い順）

**信頼性**

- **見本データへの退避が6か所以上ある。** AIクローラー取得状況、エージェントのヒートマップ重ね表示、AI流入、クロール側クライアント、突合の要約、ML の結果。`/api/ml/insights` は「作り物かどうか」の印を応答から落としている（`route.ts:28-37`）［確認済］。
- **画面なら「見本」と書けるが、API / MCP では書いても読まれない。** AI は返ってきた数字を事実として扱う。

**収集**

- **HTTP型のAIクローラーは JS を実行しない。** 今の計測には一切映らない。ログ取り込みは新規開発になる。
- **名乗り（User-Agent）は偽装できる。** 公開されているIP帯や逆引きで確かめ、「確認済み／自称／不明」の段階を付ける。
- **ブラウザ操作型エージェントは、普通の Chrome を使われると JS では見分けられない。** 「検出できた分」と明示する。署名つきで名乗るエージェントが出てきているが、これもサーバー側でしか見えない（最新仕様は要確認）。
- **アクセスログは PV の10〜100倍の行数になる。** 画像やスクリプトの行を受けない。HTML とボットの行だけ受け、ボットは時間単位にまとめる。
- **スマホでは離脱時の送信が届かない。** 拡張の集計はすべて離脱時送信で、データが PC に偏る（基盤レビュー 1.2）。

**学習と精度**

- **データ量がニューラルネットに足りない。** 5媒体・月16万PV。CV件数は未確認。表形式のデータでは決定木系（勾配ブースティング）が精度も説明のしやすさも上。
- **「CVしそうな人」の予測と「Popup が効く人」は別物。** あえて出さない比較用グループを常に残さないと、効果は測れない。
- **ペルソナは再学習のたびに番号が入れ替わる。** API 利用者の設定が壊れる。分類に版を付け、新旧を対応づける。
- **新規顧客には学習データが無い。** 最初は規則で動かし、件数が閾値に届くまでは「データ不足」と返す。サイト横断の事前知識は、既存の統合の仕組みが24サイト以上を公開条件にしており、当面は使えない。
- **クロール側の既存モデルはテナントで分かれていない。** `linkscrawl/ml/fusion/cvr_predictor.py:33` は保存先が1ファイル固定［確認済］。別の顧客のデータで学習したモデルが混ざる。

**コスト**

- **ClickHouse のメモリ上限（4.54GiB）。** 学習用の特徴量を生イベントから作ると、今の問題に上乗せされる。要約表から作る。
- **1PVごとのサーバー問い合わせ。** 判定やおすすめを毎回サーバーで計算すると、PV に比例して費用と遅延が増える。
- **AI（LLM）の利用は文章化だけに絞る。** 数字の計算には使わない。チケット単位で結果を保存して再利用する。

**セキュリティ**

- **MCP 特有の攻撃面。** ページ名、URL、クリックした文言、User-Agent は外部の人が自由に書ける文字列で、それが AI に渡る。指示文の混入を前提に、データと指示を分けて返す。
- **配信APIの鍵が漏れると、全顧客サイトへの改ざん手段になる。** 任意の HTML や JS は受けない。型どおりの部品だけにする。停止スイッチは環境変数ではなく、即時に切れる形にする（現状は Vercel の設定変更が必要）［報告］。
- **テナントを呼び出し側の自己申告で受けない。** クロール側が構造データの出口を外した理由がこれ。鍵からサーバー側で決める。
- **SQL の組み立ての穴。** `lib/llm/hybrid-query.ts:1692` ほか3か所。分析ツールを外部に出す前に必ず直す（基盤レビュー 3.2）。
- **同意前に訪問者 Cookie が作られている**［報告］。生の URL と参照元も加工なしで保存される。個人に合わせたおすすめを出すなら、同意の扱いが前提条件になる。

### 2.2 設計案

全層に共通する約束：**見本データへの退避をやめ、無いものは「未収集」「データ不足」と理由つきで返す。**

| 層 | 方針 |
|---|---|
| 収集 | JS は1ファイルに統合し、scroll は累積値の上書き送信に。ログは署名つきの受け口を1本作り、HTML とボットの行だけ受ける |
| 保存 | 生イベントは正しい並び順で作り直し、「1セッション×1ページ」の要約表を日次で作る。分析も学習もこの要約表だけを読む |
| 学習 | Python の1か所に集約する。モデルはテナントごとに分け、件数・精度・学習日を台帳に残す |
| 配信 | 夜間に計算した結果をエッジに置き、ブラウザ内で規則と組み合わせて判定する。PV ごとにサーバーへ問い合わせない |

**収集**

- JS：本体＋拡張10本を1ファイルにし、版番号つき URL で長期キャッシュする。送信項目は共通定義から生成する。
- scroll：5%刻みの新深度到達時と、画面が隠れた時に累積値を上書き送信する（基盤レビュー 1.2）。
- ログ：受け口は1本（署名つきの POST）。接続先ごとの変換は外側に置く。行き先は `events` とは別の表。
- 取り込みの守り：全体で効く流量制限、テナント別の上限、失敗時の再送か退避、サーバー側まとめ書き。

**保存**

- `events_v2`：並び順にテナント・サイト・共通URLキー・日付。座標の型を広げ、受信時刻と計測スクリプトの版を持つ。
- `page_sessions`：段階1仕様 3.2 のとおり。日次ジョブで作り、再実行しても重複しない型にする。自動集計ビューは使わない。
- scroll の生データは専用の表に分け、日単位の塊ごと捨てる。
- 読み取りユーザーに、1クエリのメモリ上限とディスク退避を既定で設定する。

**学習**

- 対象ごとの方針：

| 出力 | 最初の実装 | 学習を入れる条件 |
|---|---|---|
| Popup 判定 | 規則＋比較用グループ | 離脱予測の点数を規則の材料として追加。効果は比較用グループとの差で測る |
| LP改善提案 | 規則ベースのチケット＋構造課題の「直す順」 | 学習は不要。文章化だけ AI を使う |
| おすすめ | 「このページの次に見られたページ」の集計＋内部リンクと内容の近さ | 閲覧の連なりが十分に溜まってから |
| ペルソナ | 要約表の特徴量でのグループ分け | 分類の版管理と、人による名付け |

- 件数の関門を通らないモデルは配信しない。応答は「データ不足」。
- 実行場所は Python が動く環境。Vercel の関数では学習ライブラリが動かない。

**定期処理（Inngest）**

- 今の本数（日次の要約表、日次の特徴量、週次の学習、ログのまとめ、鮮度監視）は、既存の定期実行で足りる。
- テナントごとの学習ジョブを並べ、途中失敗を個別にやり直す段階で Inngest を採用する。
- 死活監視は Inngest に載せない。監視対象と一緒に止まるため（基盤レビュー 1.3）。

**配信**

- 判定の材料（規則、訪問者の分類、ページごとのおすすめ一覧）を夜間に計算し、エッジの保存領域に置く。
- ブラウザ内で、その場の行動（スクロール、滞在）と材料を組み合わせて判定する。
- 既存の `workers/banner-runtime` を判定の配布口として復活させる。比較用グループ、同意の関門、監査記録を既に持つ。
- 表示・クリック・閉じるの記録は、既存の `scenario_match` イベントを使う。

## 3. API / SDK / MCP と LINKTH CRAWL 連携

### 3.1 共通の形

- LINKTH CRAWL と同じ重ね方：APIキー → REST `/v1`（OpenAPI つき） → MCP。
- **鍵は2種類。**
  - ブラウザ用：ページに露出する前提。イベント送信と、自サイトの判定・おすすめの取得だけ。
  - サーバー用：秘密。権限を分ける（読み取り／ログ送信／配信の公開）。
- **テナントとサイトは鍵から決める。** 引数では受けない。
- **全応答に付けるもの：**
  - 状態：`ok` / `insufficient_data` / `not_collected`
  - 根拠レベル（既存の4段階）、件数、期間、確からしさ
  - データの鮮度（いつまでの分か）
  - 網羅率（突合の場合）
- **断定数値の禁止（D-07）は API でも守る。** 「推定○件のCV損失」は返さない。
- **外部由来の文字列は、指示ではなくデータとして区別して返す。**

### 3.2 MCP ツール案

15本程度に絞る。クロール側の107本は、AI が選び間違える数。

| 用途 | ツール |
|---|---|
| 状態確認 | `ugokilink_sites_list` / `ugokilink_ingest_status` |
| 行動を読む | `ugokilink_page_stats` / `ugokilink_heatmap` / `ugokilink_funnel` / `ugokilink_query` |
| AIエージェント | `ugokilink_agent_traffic` |
| 診断 | `ugokilink_bottlenecks` / `ugokilink_fix_priority` / `ugokilink_exit_causes` |
| 判定・配信 | `ugokilink_segments` / `ugokilink_popup_dry_run` / `ugokilink_recommendations` / `ugokilink_experiment_result` |

補足：

- `ugokilink_ingest_status`：鮮度、欠損、イベント種別の内訳。最初に呼ばせる。データが無いサイトで他のツールを呼ばせない。
- `ugokilink_query`：既存の型つき分析ツール約25本の入口。生の SQL は受けない。
- `ugokilink_agent_traffic`：HTTP型（ログ由来）とブラウザ操作型（JS由来）を分け、本物確認の段階を付ける。
- `ugokilink_fix_priority`：段階1仕様 3.4。クロール連携が前提。未連携なら `not_collected`。
- `ugokilink_url_key`：URL から共通キーを返す純粋な関数。突合の検証用に公開する。
- **配信の公開は MCP から直接実行させない。** `ugokilink_popup_dry_run` で影響を見せ、公開は人の承認を挟む。

### 3.3 SDK とエッジ

- **ブラウザ SDK**（1ファイル）：`track()`、`identify()`、`decide()`、`recommend({ slot })`。
- **エッジ**：判定とおすすめの取得。読み取り専用で、キャッシュできる形。
- **サーバー SDK**（TypeScript）：REST の薄い包み。ログ送信の署名を含む。
- **ログ送信**：REST のみ。MCP には出さない。

### 3.4 LINKTH CRAWL との接続

**共通キー**

- `shared/url_canon.py` の `match_key` に統一する［確認済］。中身は「ホスト（小文字、先頭の www. 除去）＋パス＋並べ替えた問い合わせ文字列（計測用の引数は除く）」。http と https は区別しない。
- 資料が挙げる `url_match_key`（`shared/utils.py:100`）は別物。http と https を区別し、パスまで小文字にする。内部リンク集計用の簡易版で、突合には使わない。
- 保存時に両側で列として持つ。現状、UGOKI 側は生の URL を保存し、完全一致で照合している（`app/api/fusion/url-summary/route.ts:53` ほか）。
- `url_hash` は http と https を区別する。照合には使わない。

**「誰のデータか」の対応づけ**

- クロール側の Fusion / ML ツール14本は公開停止中。理由は「UGOKI MAP のテナントとクロール側のユーザーの対応が未構築」（`linkscrawl/mcp_tools/tools.py:2084-2102`）［確認済］。
- 提案：**ドメインの所有確認で結ぶ。** クロール側は所有確認の仕組みを持つ（DNS、meta、ファイル）。同じドメインの所有を両側で確認できた組だけを連携させる。自己申告の ID に頼らない。
- 対応の台帳は1つにする。Postgres の `tenant_sites` には連携用の列が既にある。

**データの流れ**

- **持ち主が出す。** 構造はクロール側の認証つき API から、行動は ugokilink の API から。
- クロール側が UGOKI の ClickHouse を直接読んで集計し、書き戻す現在の往復はやめる（段階1仕様 2.2）。
- セクション別の行動は、クロール側が Y座標の帯を渡し、ugokilink が到達・滞在・クリックを返す形にする。

**Y座標の突合に必要な追加**

- ページ全体の高さ。毎回送られているのに、保存時に捨てられている（`worker.ts:238`）。
- 画面幅の区分。クロール側の計測条件と揃える。
- 画面より短いページと、後から伸びるページの扱い（基盤レビュー 1.2）。

**機械学習の置き場所**

- クロール側に Python の実装がある（`linkscrawl/ml/fusion/` 約5,400行。ペルソナ、CVR予測、スクロール生存、セッション品質）。
- UGOKI 側の名前だけのエンジンと二重になっている。1か所に集約し、ugokilink の API からだけ出す。
- 集約先でモデルをテナントごとに分ける。

**突合が効く具体例**

- 行動データの無い新しいページのおすすめを、内部リンクと内容の近さで補う。
- 構造の課題を、実際に困った人数で並べ替える（段階1仕様）。
- 離脱の要因を、速度・操作不能・内容不一致・導線なしに分ける（段階1仕様 3.6）。

## 4. フェーズ分け

### 着手前（コード変更なし）

- 確認スクリプトの実行（`scripts/fusion-precheck.mjs --review`）。**CV件数**と本番の表定義。CV件数が少なければ、フェーズ4と5の設計が変わる。
- `CRON_SECRET` の設定、旧 Inngest ジョブの停止（基盤レビュー 6章）。
- 5媒体の構成（CDN、CMS）。ログの最初の接続先を決める材料。

### フェーズ

| 順 | 出すもの | 中身 |
|---|---|---|
| 1 | 嘘をつかない読み取りAPI | APIキー、見本退避の除去、要約表、読み取り5〜6本を REST と MCP で公開 |
| 2 | 計測と保存の作り替え、ログ取り込み | 計測の1ファイル化、名前ずれ解消、保存の作り直し、ログ受け口と最初の接続先1つ |
| 3 | 構造との突合 | 所有確認による連携、直す順、セクション別の行動 |
| 4 | 配信 | エッジ判定の復活、規則＋比較用グループ、閲覧の連なりによるおすすめ初版 |
| 5 | 学習の自動化 | テナントごとの学習ジョブ、モデル台帳、ペルソナ |

**順序の理由**

- **1が最初**：既存データだけで成立する。社内5媒体で「どのページがどこで詰まっているか」を AI に聞ける状態が最短で出る。APIキーと応答の形は、以降の全フェーズの土台になる。
- **2が次**：1で出した数字の欠け（スマホの偏り、捨てられている値）を直す。ログ取り込みはここで初めて入る。
- **3は1の後なら2と並行できる**：クロール側のリポジトリにまたがる。
- **4が後ろ**：顧客サイトに書き込む。信頼できる信号と比較用グループが先に要る。
- **5が最後**：学習はデータ量と、4で入れた比較用グループの結果が前提。

**各フェーズの完了条件**

1. 社内5媒体で、MCP 経由の数字が検証用 SQL と一致する。公開したどの経路からも見本データが返らない。他テナントの鍵でデータが返らない。
2. スマホと PC で離脱時データの到達率に大きな差が無い。scroll の行数が9割以上減る。重い読み取り中も書き込みが落ちない。ログ由来の AIクローラーが1媒体で見える。
3. 訪問数ベースで9割以上のページが構造データと一致する（段階1仕様 5章）。
4. 比較用グループとの差が、根拠レベルつきで返る。停止スイッチが即時に効く。
5. 学習ジョブが失敗した媒体だけをやり直せる。件数不足のモデルが配信されない。

**二重レビューの対象**：フェーズ1の APIキーとテナント決定、SQL の組み立ての修正、フェーズ2の表定義、フェーズ3の連携、フェーズ4の配信、フェーズ5の学習パイプライン。本番への表定義の適用はオーナー作業。

## 5. 判断ポイント

- **機械学習の置き場所：Python 1か所に集約（推奨）** → クロール側の既存実装を引き取り、UGOKI 側の名前だけのエンジンは捨てる。両方残すと、同じ問いに2つの答えが出る。
- **既存画面：実データの5画面は社内確認用に残し、機能追加を止める（推奨）** → API の数字を目で確かめる手段が残る。全部切ると保守は減るが、数字の誤りに気づく手段を失う。
- **Inngest：フェーズ5で採用（推奨）** → 基盤レビューでは「つなぎ直さない」を勧めた。テナントごとの学習ジョブを並べる段階では採用が妥当。今入れると、管理するサービスが1つ増えるだけ。
- **ログの最初の接続先：5媒体が実際に使っている基盤に合わせる** → Cloudflare のログ転送は上位プラン限定のはず（要確認）。媒体が WordPress なら、既存の AIreceipt 側の記録を使うほうが早い可能性がある。
