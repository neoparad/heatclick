## 1. 位置づけ

### 1.1 突合の終着点

行動データ（UGOKI MAP）と構造データ（LINKTH CRAWL）の突合で出す価値を、次の一文に絞る。

> 構造の問題を、実際に困った人数で並べ替え、直したら効いたかまで確かめる。

監査ツール単独でも、ヒートマップ単独でも出せない。

### 1.2 突合でしか答えられない問い

| 問い | 構造側が出すもの | 行動側が出すもの |
|---|---|---|
| どの問題から直すべきか | 検出された課題 | 影響を受けた訪問数・離脱 |
| ページのどこで、なぜ離脱するか | セクションの文字量・画像・CTAまでの距離 | セクション別の到達率・滞在 |
| 直したら効いたか | クロール差分から変更日を検出 | 変更前後の行動の差 |
| 張ったリンクは使われているか | 内部リンクの構造 | 実際のページ遷移 |
| このサイトで効く型は何か | テンプレート・構造の特徴 | ページ群どうしの行動比較 |

### 1.3 4段階のうちの1段目

| 段階 | 出すもの | 必要な変更 |
|---|---|---|
| **1（本書）** | 課題の「影響順」一覧（ページ単位） | 計測変更なし。表1つと日次ジョブ |
| 2 | セクション診断 | 計測・保存・クロール契約の3か所 |
| 3 | 変更検知と効果検証 | 定期クロールと差分の保存 |
| 4 | サイト横断の型、機械学習 | データ量が溜まってから |

段階1を最初にする理由：ページ単位の照合だけで成立し、計測を変えずに本物のデータの画面が最短で出る。

## 2. 現状（コードで確認した事実）

### 2.1 突合画面は見本データが土台

- `app/api/fusion/url-summary/route.ts:30` は固定の見本データを作り、実データは6つの数値を上書きするだけ。セクション名・構造・検索流入は見本のまま。
- 実データの照合は URL の完全一致（`:53`）。行動側には生のURLが入っているため、表記ゆれで一致しない。テナント条件も無い。
- 取り込んだ構造データの5表を、この画面は読んでいない。

### 2.2 既存のAIチャット機能 `rank_behavior_validated_fixes` の欠点

`lib/llm/hybrid-query.ts:4419-4515`。

- **同じページの課題は、全部同じ点数になる。** 行動の値がページ単位で1つなので、実質「重要度×アクセス数」の並び。課題ごとの裏取りになっていない。
- **訪問数が過大。** セクション別の到達数を足し合わせてページの訪問数にしている（`:4467`）。
- **アクセス数を対数で潰している。** 10倍のアクセス差が順位にほとんど効かない（`:4459`）。
- **行動の集計をクロール側に頼っている。** MAP の行動データをクロール側が読んで集計し、MAP が取り込み直す往復（`section_behavior_summary`）。
- **クロールIDが常に空で返る**（`:4493`）。どのクロールに基づく結果か利用側で分からない。

### 2.3 構造データの取り込み

- **取り込みのたびに同じ課題が重複登録される。** `lib/fusion/ingest.ts` は追記のみで、同じクロールを再取り込みしても弾かない。課題の表は重複を畳まない型。
- **定期取り込みは動いていない疑い。** 定期実行は GET で呼ばれるが、GET は拒否を返す（`app/api/cron/fusion-ingest/route.ts:39`）。
- **対象サイトが環境変数に手書き**（`FUSION_INGEST_TARGETS`）。サイト台帳にはジョブIDの列が既にある（`migrations/2026-11-03-fusion-site-registry.sql:23`）。
- **クロール側の出口が外されている。** `linkscrawl/api/main.py:356` で `/v1/fusion/export` の登録がコメントアウトされ、「意図的、再公開の予定なし」と書かれている。理由は、テナントIDを問い合わせ文字列で受けるため、他テナントのデータを引ける懸念。つまり現状、構造データは MAP に流れてこない。
- **契約がずれている。** クロール側は未計測の速度値を「値なし」で送るが（`linkscrawl/mcp_tools/crawl_export.py:169-179`）、MAP 側の検証は「値なし」を受けない（`lib/fusion/crawl-export-contract.ts:41-46`）。再公開しても、未計測ページが1つあれば全体が弾かれる。
- **課題の分類が種別名の部分一致で決まる**（`crawl_export.py:57-96`）。例：モバイル入力欄の課題（`input_zoom_trigger_mobile`）が "inp" に当たり、速度に分類される。
- **セクション別行動は、滞在・到達の深さ・離脱が常に0で送られる**（`crawl_export.py:311-313`）。30日分の集計が「今日」1日分として記録される（`:287`）。

### 2.4 使える既存資産

- 構造データの5表の定義（`migrations/2026-06-06-ugokicrawl-fusion-clickhouse.sql`）。テナント列が並び順の先頭にあり、設計は妥当。
- クロール側と1バイト単位で一致する URL 正規化（`lib/url/normalize-url.ts`）。
- CV の定義と判定式（`lib/conversions/predicate.ts`）。
- 空振り・連打クリックは種別として既に記録されている（`public/v2/tracking.js:541`）。

## 3. 仕様

### 3.1 並び順の考え方（中心）

課題の種類ごとに「突き合わせる行動」を決め、つながりの強さを3段階で表示する。

| 課題の種類 | 突き合わせる行動 | つながり |
|---|---|---|
| リンク切れ、押せないボタン | その要素・そのリンク先が実際に押された回数 | 直接一致（観測） |
| 表示速度 | 読み込み直後の離脱率と、サイト基準との差 | 症状一致（推定） |
| 内容の薄さ、導線不足 | 読まれた深さ、次のページへ進んだ割合 | 症状一致（推定） |
| レイアウト崩れ | 連打・空振りクリックの率 | 症状一致（推定） |
| 検索向け設定（タイトル重複など） | 訪問数のみ | 露出のみ |

課題の種類と行動の対応は、設定ファイル1つに集約する。実際に検出されている課題の種類の一覧（6章の確認5）を見てから確定する。

#### 点数

- **直接一致**：その要素・リンク先を押したセッション数。
- **症状一致**：影響を受けた訪問数 ×（そのページの症状の率 − 基準の率）。差が負なら0。
- **露出のみ**：訪問数 × 重要度の重み。別タブに分け、上の2つと混ぜない。

基準は「同じ端末・同じディレクトリのページ群の中央値」。ディレクトリ内のページが少ない場合はサイト全体の中央値に落とす。

#### 表示の約束

- **2つの事実を別々に出す。** 訪問数と、症状の率（基準との差つき）。
- **「推定○件のCV損失」のような断定数値は出さない。** 根拠レベルの原則（D-07）に従う。
- **つながりの段階をバッジで出す。** 直接一致は「観測」、症状一致は「推定」。
- **30日で訪問100未満のページは「データ不足」とし、症状では並べない。**
- **同じ課題が多数のページにある場合は1行にまとめる。** 「サイト共通・412ページ」のように出し、内訳は展開で見せる。

### 3.2 行動側の表（新設・1つ）

名前の案：`page_sessions`。

- **1行は「1セッション×1ページ×1日」。**
- **並び順は「テナント→サイト→ページのキー→日付→セッション」。**
- **持つ値**：端末、最大到達率、滞在（そのページでの最初と最後のイベントの差）、ページ表示回数、クリック数、空振り数、連打数、入口か、出口か、直帰か、CVしたか、流入元（参照元とUTM）。
- **日次ジョブが前日分を生データから集計して入れる。** 自動集計ビューは使わない（挿入のたびに断片が増える問題を避ける）。
- **再実行しても重複しない型にする。** 同じキーの行は後勝ちで畳む。
- **初回は過去30日分を1日ずつ埋める。**
- **行数はPV数とほぼ同じ。** 累計で約120万行、月16万行。どの集計も軽い。

この表は段階1専用ではない。ヒートマップの scroll / exit 表示とセグメント絞り込みも、ここから読めば生データの全走査が不要になる。

#### ページのキー

- **「小文字のホスト（先頭の www. 除去）＋パス（末尾スラッシュ除去）」。** クエリ文字列と # 以降は落とす。
- **行動側も構造側も、同じ1つの関数で作る。** 表記ゆれによる取りこぼしを無くす。
- **制限**：クエリ文字列でページが分かれるサイト（`?p=123` 型）は区別できない。対象5媒体では問題にならない見込みだが、網羅率（3.4）で監視する。

#### 行動の定義

- **離脱・直帰は「セッション最後のページ」で判定する。** 離脱イベントはスマホで届かないため使わない。
- **空振りクリックは、リンク先を持たないものだけ数える。** 深い階層のリンク内クリックが空振りに誤分類されるため（`lib/conversions/predicate.ts:10` に記載の既知問題）。
- **ボット判定されたセッションは除外する。**
- **CV は既存の CV 定義の判定式をそのまま使う。**
- **日またぎのセッションは日ごとに別行になる。** 入口・出口の判定に小さな誤差が出るが、段階1では許容する。

### 3.3 構造側の取り込み修正

前提として、構造データの入口を開け直す必要がある（2.3）。方法は2つ。

- **既存の認証つきAPIから取る（推奨）。** クロール側の通常のAPI（APIキーで利用者を特定する）の課題出力を使う。MAP 側には接続用のクライアントが既にある（`lib/linkscrawl/client.ts`）。外された出口の懸念（テナントIDを自己申告で受ける）を持ち込まない。
- **外された出口を直して再公開する。** テナントごとの鍵の検証を足す。契約のずれも同時に直す。

どちらでも、次を満たす。

- 速度値の「値なし」を受けられるようにする。0で埋めない（未計測が最速に見えるため）。
- リンク切れの「リンク先」を項目として受け取る。検出時点では持っている（`linkscrawl/analyzer/issue_detector.py:2220-2221`）が、今の出力には含まれない。「直接一致」に必須。
- 対応表（3.1）は分類ではなく、課題の種別名で引く。分類は部分一致で決まっており、誤りがある。
- セクション別行動はクロール側から受け取らない。行動の集計は MAP 側の持ち場とする。

そのうえで、MAP 側の取り込みを直す。

- 定期ジョブを GET で動くようにする。認証は既存の共通関数のまま。
- 対象サイトはサイト台帳のジョブIDから取る。環境変数の手書きをやめる。
- 取り込み済みのクロールIDは飛ばす（`crawl_runs` を先に見る）。
- 取り込み時に、課題と速度の各行へページのキーを付ける。
- 失敗したサイトがあれば通知する。黙って失敗させない。

### 3.4 API

`GET /api/fusion/fix-priority`

- **入力**：期間（既定30日、7〜90日）、端末、つながりの段階、課題の分類。
- **認証**：既存の `requireActiveTenantSite`。全クエリにテナント条件とサイト条件を入れる。
- **入力値はすべて名前つきの引数で渡す。** 文字列の連結でSQLを作らない。
- **見本データへの退避はしない。** クロール未取り込みなら「未取込」と返す。
- **返す内容**：
  - クロールの情報（クロールID、実施日、ページ数）
  - 網羅率（行動データと一致したページの割合、訪問数ベースの割合、アクセスがあるのにクロールに無いページ数）
  - 行の一覧。各行に課題名、範囲、訪問数、症状の率、基準の率、つながりの段階、根拠レベル、根拠データへの参照、確からしさ、推奨。

集計は1つのモジュールにまとめ、画面用のAPIとAIチャットの既存機能の両方がそれを呼ぶ。数字の食い違いを防ぐ。

### 3.5 画面

- **上部に網羅率の帯。** 最新クロール日、一致したページの割合、期間。
- **「アクセスがあるのにクロールに無いページ」を件数で出す。** どこからもリンクされていないページか、クロール範囲の漏れを示す。それ自体が発見になる。
- **一覧は20行程度。** 課題名（平易な日本語）、範囲（1ページ / Nページ）、訪問数、症状と基準の差、つながりのバッジ、推奨、該当ページのヒートマップへのリンク。
- **タブは2つ。**「行動で裏取りできたもの」と「検索向け（行動では測れないもの）」。
- **既存の見本データの画面**（`app/(proof)/fusion/page.tsx`）**は、この画面に置き換えるか、見本であることを明示する。**

### 3.6 離脱要因の内訳（追加案）

3.1 の対応表を逆向きに読むと、「このページの離脱は何が原因か」の内訳が出せる。出口になったセッション1件ずつを、最後の様子から規則で分類する。

| 分類 | 判定に使う事実 |
|---|---|
| 速度 | 表示が終わる前に離脱（滞在が、そのページの表示完了時間より短い。スクロールなし） |
| 操作不能・リンクエラー | 最後の操作が、空振り・連打・リンク切れ先へのクリック |
| 冒頭で不一致 | 表示後すぐ、浅い位置で離脱（期待と内容のずれ、または内容の薄さ） |
| 読了後に導線なし | 深くまで読み、十分滞在し、クリックせず離脱 |
| 不明 | 上のどれにも当たらない |

- **ページごとに割合で出す。** 例：「冒頭で不一致 41%、読了後に導線なし 22%、速度 18%…」。
- **「不明」を必ず残す。** 無理に割り振らない。
- **根拠レベルは「推定」。** 規則による分類で、原因の証明ではない。
- **「読了後の離脱」は悪いとは限らない。** 記事を読み終えて満足した離脱を含む。CV や次ページへの導線が目的のページでだけ課題として扱う。
- **必要な追加**：`page_sessions` に「最後の操作の種類」を1列足す。表示完了時間は、クロールの計測値か、実ユーザーの計測値（既存の `web_vitals`）を使う。

## 4. 既知の限界

- **症状一致は相関で、原因の証明ではない。** 直帰率が高いのは課題のせいではなく、流入元のせいかもしれない。流入種別は保存時に捨てられているため、段階1では補正しきれない。「推定」止まりにする理由。
- **ページ単位なので「ページのどこか」は言えない。** 段階2で扱う。
- **「直したら効いたか」は言えない。** 段階3で扱う。
- **クロールと行動の時期のずれ。** クロール後にページが変わっていても検知できない。クロール実施日を画面に出して判断材料にする。

## 5. 完了の判定

1. 画面の数字が、検証用SQLの結果と一致する。本番 ClickHouse は開発環境から届かないため、検証スクリプトを許可された接続元で実行する。
2. 訪問数ベースで9割以上のページが構造データと一致する。
3. 取り込みを2回流しても、課題の件数が変わらない。
4. 他テナントのサイトIDを指定しても、データが返らない。
5. わけがいの上位10件を編集担当が見て、納得できる並びになっている。

5は数値では測れないが、最も重要。納得できない並びなら、対応表（3.1）を見直す。

## 7. 作業の単位と順序

| 順 | 作業 | 二重レビュー |
|---|---|---|
| 1 | 構造データの入口を開け直す（3.3）。そのうえで取り込みの修正（GET対応、重複防止、台帳参照）、サイト台帳へのホスト名とジョブIDの登録 | 要（テナント分離） |
| 2 | `page_sessions` の定義、日次ジョブ、過去30日の埋め戻し | 要（本番への定義適用） |
| 3 | 集計モジュールとAPI、検証スクリプト | 要（テナント分離） |
| 4 | 画面 | 不要 |
| 5 | AIチャット既存機能の付け替え | 要（AIへの指示文の変更を伴う場合） |

1と2は並行できる。3は2の後。本番への定義適用はオーナー作業。

## 8. 判断ポイント

- **行動側の表：新設する（推奨）** → 集計が軽くなり、ヒートマップの深さ表示もここから読めるようになる。表の追加は本番への定義適用が必要。新設しないなら変更は小さいが、毎回30日分の生データを読み、今のメモリ問題に上乗せされる。
- **既存のチャット機能：作り直して共通化（推奨）** → 並び順が課題ごとの裏取りになる。現状維持なら、画面とチャットで順位が食い違う。
