## 領域別 詳細評価

### 1. データ設計 — 92点

**良い点**
- eventsテーブル一本化の判断は正しい。パーティション（月別）、ソートキー（site_id, timestamp）が分析ワークロードに最適
- CVデータ（`conversion_type`, `conversion_value`, `event_revenue`）がeventsテーブルに組み込まれており、行動×CV分析が1クエリで可能
- マルチテナント対応（`site_id`, `org_id`）がスキーマレベルで組み込まれている

**残存する問題（-8点）**
- [ ] **read_yの型不一致**: `UInt16 DEFAULT 0`で定義したが、`track/route.ts` L112で`event.read_y || null`を書き込んでいる。UInt16にnullは入らない。`Nullable(UInt16)`にするか、書き込み側を`|| 0`に修正する必要がある
- [ ] **IDの衝突リスク**: `Date.now()-Math.random().toString(36).substr(2,9)` で生成。高トラフィック時にミリ秒が同一＋乱数衝突の可能性がある。UUIDv7またはClickHouseの`generateUUIDv4()`を使うべき
- [ ] **read_duration/read_yの空間効率**: 全イベント行にread_y/read_durationが存在するが、read_areaイベント以外ではゼロ。ClickHouseのカラムナストレージで圧縮は効くが、スキーマの意図が曖昧

---

### 2. インフラ設計 — 85点

**良い点**
- ClickHouse + Redis + Inngestの3層構成は正しい
- Redisバッファリング→Inngestフラッシュのアーキテクチャは理にかなっている
- warmCacheのデバイス×タイプ拡張は完了

**残存する問題（-15点）**
- [ ] **popEventBufferのN+1問題**: LPOPを最大500回ループしている。Redisへの往復が500回発生する。`LRANGE 0 499` + `LTRIM 500 -1`の2コマンド、またはRedis pipelineを使うべき。**これは性能に直結する問題**
- [ ] **リトライバッファの制御不足**: `flushEventBuffer`は毎分cronで実行されるが、リトライバッファも毎分処理される。コメントには「5分に1回程度」と書いてあるが制御がない。カウンターまたはタイムスタンプで頻度制御すべき
- [ ] **バッファの永続化保証**: Redisが再起動するとバッファ内のデータが消える（永続化設定次第）。Redisの`appendonly yes`設定が必須だが、インフラ側の設定が保証されていない
- [ ] **pushEventBufferのメモリ効率**: 1回のRPUSHで全valuesをJSON文字列化。valuesが大きい場合（バッチ10イベント×複数テーブル）、個別のRPUSHに分割する方が安全

### 3. トラッキング設計 — 88点

**良い点**
- コア+拡張5モジュールへの分割は正しい設計判断
- data-extensions属性による選択制御
- sendBeacon優先、PIIマスク、dead/rage click検出

**残存する問題（-12点）**
- [ ] **コアが8.6KB（minified）**: 目標5KBに対して1.7倍。`sanitizePII`, `sanitizeUrl`, `getElementPath`, `getRootDomain`等のユーティリティをコアから`tracking-ext-utils.js`に分離し、必要な拡張がimportする形にすれば5KB近くまで削れる
- [ ] **グローバルAPI改ざんリスク**: `window.ClickInsight.utils`と`config`がグローバルに公開されている。第三者スクリプトから`window.ClickInsight.config.apiEndpoint`を書き換えてデータを別サーバーに飛ばせる。`Object.freeze(window.ClickInsight)`すべき
- [ ] **拡張ロード順序の保証なし**: `document.head.appendChild(script)`で拡張を読み込むが、ロード完了順序が保証されない。現時点で拡張間に依存はないが、将来追加する拡張に依存がある場合に壊れる。onloadコールバックチェーンの検討

---

### 4. API/バックエンド設計 — 78点

**良い点**
- middleware.tsの構造は正しい。公開API除外、JWT検証、ヘッダ注入の流れが明確
- AuthGuardのJWT検証＋リダイレクト実装
- Redis Rate Limiting + メモリフォールバック
- 共通エラーレスポンス関数（api-utils.ts）の設計

**残存する問題（-22点）**
- [ ] **verifySiteAccess()が未統合**: ヘルパー関数は作られたが、**20+の既存APIルートのどこからも呼ばれていない**。sites, heatmap, statistics, clicks等の全APIで`getAuthContext()`→`verifySiteAccess()`を呼ぶ必要がある。これが未完了の間はマルチテナント分離は実質未実装
- [ ] **共通エラー関数が未適用**: `apiError()`, `badRequest()`等を作ったが、既存の20+のAPIルートは従来の`NextResponse.json({error:...})`のまま。全ルートに適用して初めて意味がある
- [ ] **verifySiteAccess()のセキュリティホール**: catch節でDB接続エラー時に`authorized: true`を返している（L84）。本番環境でDBが一時的に落ちた場合、全ユーザーが全サイトにアクセスできてしまう。`authorized: false`に修正必須
- [ ] **CORS設定が全オリジン許可**: `origin: request.headers.get('origin') || '*'`は任意のオリジンを許可。`/api/track`は外部サイトから呼ばれるので緩くて良いが、その他のAPIは管理画面のドメインに限定すべき
- [ ] **JWT secretのハードコードフォールバック**: `'ugokimap-default-secret-change-in-production'`。環境変数が未設定のまま本番デプロイされると全環境で同じsecretが使われる。フォールバックを削除し、未設定時はエラーで起動を停止すべき
- [ ] **middleware L94のページルートチェック**: 巨大な`||`チェーン。`matcher`設定と重複しており、新しいページ追加のたびに2箇所を変更する必要がある。matcherに任せてmiddleware内のチェックを簡素化すべき

## 総評

**設計のポテンシャルは極めて高い。** 「クリック座標×画像視認時間×CV」を要素レベルで突き合わせられるプロダクトは市場に存在しない。AI診断とMCP提供を組み合わせた時の破壊力は、既存のヒートマップツールとは完全に別カテゴリになる。

**現在の82点は「設計は正しいが仕上げが甘い」状態。** 穴は全て「繋ぎ込みの甘さ」であり「設計の間違い」ではない。Phase 1-2（計3-5日の作業）で92点に到達でき、競合と戦えるラインに入る。

データ設計（92点）がこのプロダクトの最大の資産。ここが弱いと後から直すのは困難だが、UGOKI MAPはここが既に強い。
