# P0 計測プロトコル — ヒートマップ表示速度 (オーナー向け)

> 作成: 2026-07-19 (Sonnet 5)
> 元指示: `docs/heatmap/SONNET_PROMPT_P0_instrumentation_2026-07-19.md` §5
> 想定読者: 非エンジニアのオーナー。ブラウザの「検証ツール (DevTools)」を F12 で開く程度の操作は本書内で説明します。エンジニア知識は前提にしません。

## 0. この文書の目的と前提

ヒートマップ画面の「表示に 10〜12 秒かかっている」という体感を、**どの区間にどれだけ時間がかかっているか**を数字で裏付けるための計測手順です。速度改善そのものはこの文書の範囲外です（先に計測 → 原因の内訳を確定 → その後に改善、の順番で進めます）。

前提:
- サーバ側の計測コード（Server-Timing / ログ出力）と、クライアント側の計測コード（`?perf=1` で有効化される計測）が本番にデプロイ済みであること。まだの場合はエンジニア（Sonnet 5 チーム）にデプロイ状況を確認してください。
- 計測中に取得するスクリーンショットや HAR ファイルには本番 URL・内部情報が写り込みます。社外に共有する際は事前にエンジニアに確認してください。

## 1. 「2秒」の定義を決めてください（オーナー承認事項）

「ヒートマップが2秒で出るようにしたい」という目標を計測可能にするには、**「出た」の瞬間をどこにするか**を先に1つに決める必要があります。以下の3択から選んでください。

| 選択肢 | 「出た」と判定するタイミング | 説明 |
|---|---|---|
| (a) | ヒートマップの色（オーバーレイ）が最初に画面に現れた瞬間 | 背景の実ページ画像がまだ読み込み中でも、色の重なりだけが見えている状態を「完了」とみなす |
| (b) **推奨** | 実ページのスクリーンショット画像とヒートマップの色の両方が揃って表示された瞬間（「視覚完成」） | ユーザーが実際に「意味のある画面が見えた」と感じるのはこの瞬間に近いと考えられる。エンジニア側では `hm:visual-complete` という名前で計測します |
| (c) | サイドパネルの数値・要素一覧など、画面上の全部品が出そろった瞬間 | 最も厳しい基準。細部の情報まで含めて「完全に使える状態」になった時点 |

**推奨理由（(b) について）**: 色だけ出ても背景画像がなければ「どこがクリックされているか」がわからず実用的な完了とは言えません。逆に (c) はサイドパネルの数値表示などヒートマップ本体と直接関係ない部分まで含んでしまい、目標設定としてはノイズが混ざります。そのため (b) を「視覚完成」の基準として推奨しますが、最終判断はオーナーにお任せします。

### 承認欄

```
選択: [ ] (a)   [ ] (b)   [ ] (c)
承認者:
承認日:
備考:
```

この選択結果は、以降の計測データを「2秒」という目標と比較する際の基準になります。エンジニアチームに選択結果を伝えてから次の計測に進んでください。

## 2. 計測手順 — 3 シナリオ × 3 回（合計9回）

### 2.1 なぜ3シナリオ必要か

同じページでも、アクセスするタイミングによって速度が大きく変わります（サーバの「起動が遅い1回目」と「温まっている2回目以降」で数秒単位の差が出ます）。原因を区間ごとに切り分けるには、この違いを分けて計測する必要があります。

| シナリオ | タイミング | 目的 |
|---|---|---|
| ① 初回アクセス | その日の最初に開く | **最重要**。サーバの cold start（起動待ち）を含む、最も遅いパターンを計測 |
| ② 直後にリロード | ①の直後にページを再読み込み | warm 状態（起動待ちなし）の速度を計測 |
| ③ 5分後に再訪問 | ①・②から5分ほど間を空けて開く | サーバが再び冷えた（or 中間状態の）タイミングでの速度を計測 |

これを ①②③ それぞれ3回ずつ、合計 **9 回** 計測します。同じ条件でも毎回ゆらぎがあるため、1回だけでなく複数回のデータを取ります。

### 2.2 1回あたりの操作手順

1. ブラウザ（Chrome 推奨）で対象ページを開く**前に** DevTools を起動する。
   - Windows: `F12` キー、または画面を右クリック →「検証」
2. DevTools 上部のタブから **Network（ネットワーク）** タブを選び、「Preserve log（ログを保持）」にチェックを入れる。
3. 同じく **Console（コンソール）** タブも見える状態にしておく（Network と Console は別ウィンドウ・別タブで並べて開いても構いません）。
4. アドレスバーに、普段ヒートマップを開いているURLの末尾に `perf=1` を付けて開く。
   - URL に `?` がまだ無ければ: `?perf=1` を末尾に追加
   - すでに `?site=xxx` のように `?` が付いている場合は: `&perf=1` を末尾に追加
   - 例: `https://ugokimap.com/heatmap?perf=1`（実際のURLは既存のものに合わせてください）
5. ページが完全に表示されるまで、**何もクリックせず、他のタブにも移動せず**待つ（詳細は §3 参照）。
6. 表示が完了すると、Console タブに自動で表（`console.table`）が出力されます。これが計測結果の本体です。**この表全体が見えるようにスクリーンショットを撮る**。
7. Network タブに切り替え、リストのどこかで右クリック →「Save all as HAR with content」を選び、HAR ファイルとして保存する。
8. スクリーンショットと HAR ファイルは、わかりやすいファイル名で保存する。
   - 例: `scenario1_run1_20260719_0905.png` / `scenario1_run1_20260719_0905.har`

## 3. 計測中の注意事項（最重要・必ず守ってください）

**計測を始めたら、計測が終わるまで他のヒートマップ操作を一切しないでください。**

理由: このヒートマップ機能には「他デバイスの先読み（自動プリフェッチ）」という仕組みがあり、画面を触ったタイミングを起点に **+4秒後・+8秒後** に追加のバックグラウンド通信が自動で走ります。この通信が計測中の Network タブに紛れ込むと、「本来のページ表示にかかった時間」と「先読み通信の時間」が区別できなくなり、計測結果が実態より悪く（遅く）見えてしまいます。

対応ルール:
- 1回の計測中（ページを開いてから `hm:visual-complete` の表が出るまで）は、クリック・スクロール・別タブ移動をしない。
- もし誤って他の操作をしてしまった場合は、**その操作をした時刻以降に発生したネットワークリクエストは分析対象から除外する**と HAR / スクショにメモを残してください（上の記録シートの「備考」欄に記入）。
- 同じPC・同じネットワークで、計測中に別の人が同時にヒートマップを開かないようにしてください（プリフェッチが混線する原因になります）。

## 4. Clarity との比較計測（対照実験）

自社のヒートマップの遅さが「業界的に普通」なのか「明らかに遅い」のかを判断するため、同一 PC・同一ネットワーク環境で Microsoft Clarity の同等画面（ヒートマップ／レコーディング表示画面）を1回計測し、比較の基準値とします。

### 手順

1. §2.2 の手順1〜3と同様に、Clarity を開く**前に** DevTools（Network + Console）を準備する。
2. Clarity にログインし、自社サイトの、今回計測した自社ヒートマップとできるだけ近い内容の画面（例: 同程度のトラフィック量のページのヒートマップ／レコーディング一覧）を開く。
3. 画面が表示され終わるまでの時間を、DevTools の Network タブで確認する。
   - 目安として: 最初のリクエストの開始時刻から、目に見える形でヒートマップ相当のデータが表示されるまでの時間（Network タブの Waterfall 上でどこまでが「読み込み中」か目視で確認）
   - Clarity 側は Server-Timing や `?perf=1` のような自社計測はないため、DevTools 上の目視・Network タブの完了時刻で代用する
4. スクリーンショットと HAR を保存する（例: `clarity_comparison_20260719.png` / `.har`）。
5. 同一 PC・同一回線であることを記録に残す（別のPCや別の回線だと比較が成立しないため）。

この計測は1回で構いません（Clarity 側の内部実装の詳細分析が目的ではなく、あくまで「体感速度の相場観」を実数で持つためのものです）。

## 5. ClickHouse query_log 計測（operator 向け・実行はオーナー or Codex Desktop）

サーバ側の計測（§2 の Server-Timing）だけでは「ClickHouse への問い合わせ自体が何ミリ秒かかったか」「何行読んだか」まで裏取りできません。より正確に裏取りするために、ClickHouse 本体のログ（`system.query_log`）を限定権限で参照します。

**この節の SQL 実行は Sonnet 5（本実装エージェント）は行いません。オーナー、または ClickHouse に管理者権限を持つ Codex Desktop 側で実行してください。** ここでは実行してもらうための SQL 雛形だけを用意します。

### 5.1 限定ロールの作成（最小権限のユーザーを新規作成）

以下を ClickHouse の管理者権限で1回だけ実行してください。パスワードはこの文書やチャットには書かず、別途強力なパスワードを生成して安全な方法（社内パスワードマネージャー等）で管理してください。

```sql
-- 1. 計測専用の限定ユーザーを作成（パスワードは <PASSWORD_HERE> の部分を安全に生成した値に置き換える）
CREATE USER IF NOT EXISTS perf_observer IDENTIFIED BY '<PASSWORD_HERE>';

-- 2. system.query_log の、計測に必要な列だけを SELECT 許可（それ以外のテーブル・列には一切アクセスできない）
GRANT SELECT(
  query,
  query_duration_ms,
  read_rows,
  read_bytes,
  result_bytes,
  event_time,
  type,
  query_kind,
  log_comment
) ON system.query_log TO perf_observer;
```

補足:
- `query` 列には実行された SQL 文そのものが含まれます。tenant の実データそのものは含まれませんが、社内以外への共有は避けてください。
- 計測が終わったら、以下で後片付けしてください（限定ロールとはいえ、不要になったアカウントは残さない）。

```sql
-- 計測終了後の後片付け
DROP USER IF EXISTS perf_observer;
```

### 5.2 集計クエリ（log_comment で heatmap のリクエストだけに絞り込む）

サーバ側の計測コードは、ヒートマップ関連の全 ClickHouse クエリに `log_comment` として `{"app":"heatmap","route":"...","span":"...","req":"..."}` という JSON を付与しています。これを使えば、`system.query_log` の中から heatmap のクエリだけを正確に抜き出せます（他の調査クエリや health check が混ざりません）。

**route・span ごとの内訳集計（どの区間が遅いかを一目で見る）:**

```sql
SELECT
  JSONExtractString(log_comment, 'route') AS route,
  JSONExtractString(log_comment, 'span')  AS span,
  count()                                 AS n,
  quantile(0.50)(query_duration_ms)       AS p50_ms,
  quantile(0.95)(query_duration_ms)       AS p95_ms,
  max(query_duration_ms)                  AS max_ms,
  quantile(0.50)(read_rows)               AS p50_rows,
  quantile(0.95)(read_rows)               AS p95_rows,
  quantile(0.50)(read_bytes)              AS p50_bytes,
  quantile(0.95)(read_bytes)              AS p95_bytes,
  quantile(0.50)(result_bytes)            AS p50_result_bytes,
  quantile(0.95)(result_bytes)            AS p95_result_bytes
FROM system.query_log
WHERE type = 'QueryFinish'
  AND query_kind = 'Select'
  AND event_time >= now() - INTERVAL 1 DAY
  AND JSONExtractString(log_comment, 'app') = 'heatmap'
GROUP BY route, span
ORDER BY route, span;
```

読み方: `route` (`/api/heatmap` 等) と `span` (`ch` / `ch-elements` 等、サーバ側計測コードが付けている区間名) ごとに、実行回数・所要時間の中央値(p50)/95パーセンタイル(p95)/最大値、読み込み行数・バイト数がわかります。§2 で `?perf=1` 計測をした時間帯（`event_time` の範囲）に絞って実行すると、そのセッションのサーバ内訳がそのまま数字で出ます。

**特定の1リクエストだけを追いたい場合（`req` = Server-Timing/ログに出ている `reqId`）:**

```sql
SELECT
  event_time,
  JSONExtractString(log_comment, 'route') AS route,
  JSONExtractString(log_comment, 'span')  AS span,
  query_duration_ms,
  read_rows,
  read_bytes,
  result_bytes
FROM system.query_log
WHERE type = 'QueryFinish'
  AND JSONExtractString(log_comment, 'req') = '<reqId をここに>'
ORDER BY event_time;
```

`<reqId をここに>` は、Vercel の function ログ、または §2 の Console 出力に含まれる `reqId` の値に置き換えて実行してください。
